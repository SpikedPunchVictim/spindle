## What the reviewer reported

The review of e25a956 (DESIGN v0.9.38, "the host operating key is ephemeral") rejected
on F1: A10.43 claims to make A4's "they need no custody of their own" literally true,
but that sentence in A4 (:382-385) governs *two* keys -- the operating key and the
host's own envelope `DeviceKey` -- while A10.43's gloss at :386 resolves only the
operating key. The reviewer traced the forced consequence for the unresolved half:
if the DeviceKey is also never persisted, it is regenerated at every process start,
which means `host_device_fp` changes on every restart -- "a much larger consequence
than any of the three stated, and the document never says it." The implementer's own
scoping of the reject, verbatim: "The reject was half mine. `device_fp`-churns-per-
restart was already forced by A4's 'exactly one of them is persisted', which is
v0.9.32 text -- I didn't create it. But v0.9.38 *claimed* to make 'they need no
custody of their own' literally true while resolving only one of the two keys it
governs, so the claim was wrong even though the underlying fact predates it." That is
the distinction the class name `scope-mismatch` records: the fact was old, the
claim's scope was new.

Five minors followed, all rooted in the same amendment. F2 and F3 are sweep gaps: the
commit message claimed to check "every other place that states when the root loads or
what cold means," but a decision that makes the operating key non-persistent
invalidates every statement that *presupposes* it can be persisted -- and a
reinstall-from-backup line at :357-359 and a spike row at :1677 both still presuppose
exactly that. F4 and F5 are both `wrong-mechanism`: F4 claimed A10.42's local bound
check gets a tighter answer from "a freshly restarted host," when the check is
offline and reads only capabilities already held, so the tightness depends on when
those caps were issued, not on the host's uptime -- and the document states the
correct version elsewhere in the same commit (:1581) and the loose one at :391. F5
argued that reopening v0.9.31 was blocked because "a fresh nkey still cannot obtain a
fresh certificate without a restart," but the operating-key certificate stopped
carrying `nats_fp` back in A10.40, so a fresh nkey never needed a fresh certificate in
the first place -- the reviewer marked this "ARGUED, NOT DEMONSTRATED" and confirmed
via `git grep -n "KeyPair::new_user" -- crates/` that no production code path depends
on the abolished relationship. The implementer's acceptance, verbatim: "The v0.9.31
argument was a wrong-mechanism defect of exactly the class this repo's corpus tracks
-- right conclusion, invented reasoning."

F6 is `spec-cannot-execute`: A7b still gives the host op-key cert a 90-day `exp` under
"n/a (rotation)," but A10.43 mints that cert only at process start. A host process
that outlives 90 days presents an expired cert it cannot renew without a restart, and
every capability it issued expires with it. The reviewer named the two ways to close
this -- an explicit mid-process re-certification, or a stated maximum process
lifetime -- and it was resolved by the first in DESIGN v0.9.39's new A10.44; the
second was rejected because it "leaves a headless daemon to lock itself out with no
mechanism able to prevent it." Notably, the implementer had presented the custody
fork to the user without this consequence; the reviewer surfaced it, and it went back
to the user as a second fork.

Two nits closed it out. N1 is the same sweep gap as F2/F3 applied to the A12 threat
table's mitigation column. N2 is unusual for this corpus: the commit message cites
`§A4:464` and `§A4:535`, but those are pre-commit line offsets that no longer point
at the cited text once the same commit's edits land. The reviewer recovered the
intended lines with `git show e25a956^:docs/DESIGN.md` and confirmed the underlying
claims still held, but flagged the citations themselves as "a trap for the next
reader." This one is unfixed and cannot be fixed -- commit messages are immutable and
this repo does not rewrite history -- so it is logged for the corpus's count, not as
an outstanding action.

## Reading

v0.9.38 was itself a correction commit, closing a fork the review of v0.9.36 had
raised, and it shipped a defect of the same family it was correcting: a claim whose
scope did not match the sentence it was resolving. Every finding here traces back to
one root decision -- the operating key stops being persisted -- propagated
incompletely through a document that talks about that key in at least six different
places (A4's custody sentence, the key-change wall, a spike table, two mechanism
explanations, an expiry table, and a threat-mitigation column). The recurring failure
mode is not "wrong fact" but "right fact, wrong scope of sweep": F1, F2, F3, and N1 are
all a decision's consequences stopping at the paragraph being edited instead of
following the model logically. F4 and F5 show the same amendment shipping a correct
statement in one clause and a wrong explanation of the same mechanism in another,
inside a single commit. The nine-attack `td-8e239e` companion review shows the
alternative outcome from the same process, which is why both records exist side by
side.
