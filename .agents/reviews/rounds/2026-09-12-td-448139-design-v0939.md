## What the reviewer reported

The review of `0ae2fd5` (DESIGN v0.9.39, "the envelope DeviceKey is ephemeral too, and
the op cert renews") returned four rejects, four minors and four nits, under a verdict
that named the pattern rather than any single finding: "Mechanically clean;
substantively it repeats the fault it was written to fix. Two of the four newly written
'consequences to state plainly' carry wrong mechanisms, and the sweep misses the one
section v0.9.38 itself had edited for A10.43."

The two wrong mechanisms are F1 and F3, and they fail in opposite directions from the
same cause -- writing a consequence from the shape of the argument rather than from the
section that owns the fact. F1 said ephemeral device keys make A10.37's registry cache
"re-published every restart rather than occasionally," when A10.37 is an explicit user
decision (2026-09-01) that the host republishes on every host *connect*, not only after
a rotation. Every-connect is already at least as often as every-restart, so the cadence
changes by nothing; what changes is the cert's contents. The document says the correct
version one row away, at A10.44 in the same commit -- and the wrong version reinstated
precisely the reading `[corrected v0.9.27]` had already fixed once. F3 said "a host
restart reaches a client only when that client is issued a new capability," a universal
claim over every channel between host and client, written from the one channel under
discussion. The `HostDeviceCert` embeds the same `op_cert`
(`host_device_cert.rs:38`) and clients fetch it routinely from a cache refreshed on
every connect, so the restart reaches them by a second channel -- and after this very
commit it *must*, because `device_fp` changed.

F4 is the finding this record exists to preserve. The commit replaced v0.9.38's
rejected nkey argument with a new one: that a lifetime argument fails because "the NATS
connect key's seed is persisted -- OS keychain natively, IndexedDB in a browser." A10.40
retired the long-lived host nkey seed, and the keychain/IndexedDB text it leaned on sits
under "Two credentials per device," following the *Member* definition -- a member
device, not a host daemon, which has no IndexedDB. `git grep -n -iE "host .{0,20}nkey"`
returns three hits, all saying the opposite, and zero supporting it. What makes it worth
a record rather than a line item is its provenance: the commit message credits the
mechanism to the *previous* reviewer. It was adopted into the normative document without
being traced to A10.40. The reviewer's own framing: "A reviewer's assertion is not
evidence... Given this corpus's headline metric, adopting a reviewer's unverified
mechanism verbatim is the highest-risk edit in the commit."

F2 is the sweep miss, and it is recursive. v0.9.38 was rejected for a sweep whose scope
did not cover the class its decision invalidated. v0.9.39's sweep does not cover the
section *v0.9.38's own sweep had covered*: `git show e25a956 -- docs/DESIGN.md` has a
hunk that wrote the very A9b sentence now contradicted, so the implementer had already
identified A9b as in-scope for A10.43's blast radius and did not revisit it for A10.44.
F5 through F12 are the tail: a two-row table read one row deep (F5), the rejected claim
still standing unmarked in A10.43 (F6), three "fetched once and cached" statements that

## Reading

This is the third link in a chain: v0.9.36 -> v0.9.38 -> v0.9.39, in which every
correction commit carried a defect of the family it was correcting. v0.9.38 was rejected
for a scope-mismatch and a sweep gap and shipped both again; v0.9.39 was written to fix
two wrong mechanisms and shipped two new ones, one of them inherited from the report that
identified the first two. The corpus's headline metric -- the share of findings
introduced by commits whose purpose was to fix something else -- is not a curiosity here;
it is the dominant failure mode of this document's maintenance, and all twelve findings
in this record but one are `correction-commit`.

The reviewer's closing prescription is the cheapest instrument yet proposed for it: for
any commit that amends decision N, run `git show <N> -- docs/DESIGN.md | grep '^@@'` and
re-read every hunk range N touched. That single command surfaces F2 and F6 -- both sweep
misses -- before review. For F1, F3 and F4 the corpus's existing rule needs no change,
only enforcement: every mechanism sentence must be traced to the section it names and
quoted from it, *including* a mechanism handed over by a reviewer.

One further instance of the family was caught in the fixing commit itself and is logged
here for honesty rather than counted as a finding, because it never shipped. The
implementer's own brief for the F1 fix wrote the inline marker as `[corrected v0.9.40,
which had reinstated the reading v0.9.27 corrected]` -- naming v0.9.40, the correcting
version, as the one that had reinstated the bad reading. It was v0.9.39. The applier
applied it faithfully; a verification read before commit caught it and it was fixed in
place. A correction commit misattributing a correction inside its own correction marker
is the exact shape this record counts twelve of, arriving one layer deeper.
