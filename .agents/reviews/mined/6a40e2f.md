## What the commit says

> The comment justifying the post-publish `flush()` claimed "`request` used
> to flush for us". That is false: async-nats 0.35.1's `send_request`
> explicit-inbox branch -- the path this code now mirrors -- subscribes,
> publishes with a reply, and awaits, without ever flushing. The flush is
> kept deliberately, for a reason the old comment did not give [...].
> Correcting a comment that asserted something untrue is the same defect
> class A10.36 itself fixed, so it is not left to drift.

## Reading

A comment justifying why the client code calls `flush()` after publishing asserted that the previous implementation (`Client::request`) used to flush on the caller's behalf — a factual claim about a third-party library's internals that turns out to be false when the actual `async-nats` source is read. The underlying decision to keep the `flush()` call was and remains correct (confirmed by live latency measurements showing no regression either way), so this is a `wrong-mechanism` case: right conclusion, wrong stated reason. The commit itself frames this as the same class of defect A10.36 (d6e5ec71) had just fixed — an unverified claim of equivalence written into a comment and left unchallenged until someone read the library source to check it.
