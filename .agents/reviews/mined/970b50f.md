## What the commit says

> X25519 was a false premise. x25519-dalek-2.0.1/src/x25519.rs:36-41:
>
>     impl From<[u8; 32]> for PublicKey {
>         fn from(bytes: [u8; 32]) -> PublicKey { PublicKey(MontgomeryPoint(bytes)) }
>     }
>
> Infallible. Rust accepts any 32 bytes as agree_pk, exactly as TS does, so there
> was no divergence to close -- and adding the TS check the ticket asked for would
> have CREATED one.
>
> Ed25519 was real, but fixing TS alone would have opened a split the other way.
> VerifyingKey::from_bytes is only CompressedEdwardsY::decompress
> (ed25519-dalek-2.2.0/src/verifying.rs:165-173) -- it never checks y < p. Measured
> at the real call site:
>
>     bytes              Rust verify_device_certificate   noble Point.fromBytes
>     [0xff; 32]         ACCEPTS (fp mismatch later)      REJECTS
>     [0u8;31] ++ 0xa9   REJECTS InvalidPublicKey         REJECTS

## Reading

Two distinct findings sit in one commit. The consequential one (F1) is a real, shipped security-relevant divergence: Rust's Ed25519 verifier accepted non-canonical public-key encodings that TypeScript's noble library rejected, meaning the same raw bytes could produce a valid certificate/capability natively but an invalid one in a browser (or vice versa) — a cross-implementation consensus break, discovered only by measuring the real call sites rather than reasoning about the dependency's API shape. The second (F2) is a case of the ticket itself — the task specification driving this work — asserting a premise about the dependency's behavior that a five-minute read of the dependency's source disproved; had the ticket's literal instruction been followed, it would have introduced a new divergence in the process of "fixing" an imagined one. Both were caught before the fix shipped by treating the ticket's stated facts as claims to verify rather than as given.
