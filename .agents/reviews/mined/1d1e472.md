## What the commit says

> The connections-count claim in `spindle-hostd`'s docs was wrong and the
> instrumentation caught it. Four places said `run` opens three independent
> SQLite connections; it opens two, and the doc was counting the
> `SqliteStoreFactory` as a connection — then compounding it by calling the
> factory's first lazy connection "a fourth" when it would be the third.
> Corrected, with the load-bearing part preserved: the reason an in-process
> `Mutex<Store>` cannot provide atomicity is that more than one connection
> exists and none of them is excluded by an in-process lock, which is true at
> two as it was at three. Commit 0306dea's message quoted the wrong number
> from this doc.
>
> `discard_staging_bytes` leaked a staging file per failed cleanup. Verified
> this is a real leak rather than a benign miss: `reconcile_uploads_against_disk`
> walks the committed-upload ledger only and hides staging names via
> `is_staging_name`, so nothing sweeps them, and the file always exists by that
> point because `upload_open` creates it eagerly.

## Reading

While instrumenting spindle-hostd's daemon lifecycle for logging, the implementer traced the actual connection-opening call sites and found that a "three independent SQLite connections" figure — stated in four places in the docs and, notably, quoted verbatim into the commit message of a named prior security fix (0306dea, the S18 minting TOCTOU fix) — was wrong; the real count is two. The underlying security argument survives unchanged (atomicity still requires a real transaction rather than an in-process mutex whenever more than one connection exists), so this is a corrected supporting figure rather than a reversed conclusion, but it is a concrete instance of an unverified number propagating from a doc comment into a security-relevant commit message. The same commit separately confirms, by tracing rather than assuming, that a previously-swallowed cleanup failure in `discard_staging_bytes` is a genuine staging-file leak invisible to the reconciliation sweep (which only walks committed uploads).
