## What the commit says

> Nothing has ever written a revocation into the helper's store.
> `record_revocation` was implemented by both stores, the callout already
> refused revoked subjects, and `is_revoked` was wired into
> `decide_device_connect` — but the only callers were test doubles and the
> `Store` enum dispatcher. The durable revocation store §A4 leans on for
> "refuses the cap on re-auth" was, in practice, always empty.

## Reading

Every individual piece of the revocation-enforcement chain existed and appeared wired together — a storage method, a lookup used by the connect-decision function, and a callout that would honor a revocation if one were present — but no code path anywhere in the running system ever actually called the method that writes a revocation into the store. The security guarantee DESIGN.md §A4 describes ("refuses the cap on re-auth") had therefore never held in practice; it only worked in tests that used test doubles to inject revocation records directly. This is the same shape as ee53d375 and c7528af elsewhere in this range: individually-tested components that were never actually connected end to end, discovered only when someone building the next leg of the same feature (ingesting a real host-signed revocation) went looking for the production caller and found there wasn't one.
