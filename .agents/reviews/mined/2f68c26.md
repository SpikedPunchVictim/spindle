## Reading

This is a re-verification pass over the implementer's own earlier bug-hunt
report (288b608), run by independent read-only sub-agents explicitly told
not to trust the original write-up — and it found two of the implementer's
own filed findings were themselves defective. Claim 2 of td-93cee6 described
specific code (an UPDATE/DELETE that discards a rows-affected count) that the
commit says "does not exist and never did" — a finding based on describing
code from memory rather than reading it, the same failure mode the commit's
own "Method lessons" section names explicitly. td-b940b1 kept its overall
conclusion but had gotten the mechanism backwards: counter drift is
bidirectional (upload undercounts, delete overcounts) rather than the
one-directional "charged for bytes never persisted" scenario originally
filed, which the commit says the actual code ordering makes impossible. Both
are second-order findings — a review not of shipped production code, but of
the implementer's own earlier review findings about that code — and both
fit the instructions' bar of "wrong and had shipped": the false findings had
already been filed onto the td board and could have been worked as if true.
