## What the commit says

> The assertion added in d063e90 claimed the session peer log must be empty
> after a denied connect. It cannot be: that test performs a control run
> first, in which the *allowed* device completes a full session — the
> pre-existing `sessions == 1` assertion immediately above says exactly
> that — so the log holds the allowed device's fingerprint by the time the
> check runs. The assertion would have failed against a live stack.
>
> It could not fail in CI, which is the part worth noting. Every test in
> this file is #[ignore]d, so a green `cargo test --workspace` says nothing
> about any assertion in it. A wrong assertion here is invisible until
> someone brings up a real stack.
>
> Replaced with an equality check against vec![allowed.device_fp], which is
> strictly stronger than the emptiness check was meant to be: it pins both
> that the denied device never reached the session layer and that the one
> session that did happen received the correct identity.

## Reading

An assertion committed one revision earlier (d063e90) asserted something
that the test's own preceding lines already contradicted — a control run in
the same test leaves an entry in the peer log the assertion claimed would be
empty. The reason it shipped unnoticed is the sharper point: the entire test
file is `#[ignore]`d, so `cargo test --workspace` compiles the wrong
assertion but never executes it, and nothing in ordinary CI could have
caught it. This is exactly the "compiles green, never runs" shape the
schema's `unverified-coverage-claim` class describes — a claim about test
behavior with nothing actually executing it — and the commit says so almost
verbatim.
