## What the commit says

> `assert_revoked_device_cannot_reconnect` could report the < 5 s revocation bar
> met while proving nothing. Two independent defects, both found in the
> 2026-09-01 two-model review and both confirmed by mutation here.
>
> 1. The reject leg matched `Err(e) => "correctly refused"`, accepting ANY connect
> error. `base_opts` sets a 5 s `connection_timeout`, so an unreachable stack
> yields five `TimedOut` errors, which the loop counted as one refusal plus four
> confirmations and returned as a pass. Only
> `ConnectErrorKind::AuthorizationViolation` now counts as a refusal; every other
> kind is a loud panic naming the kind and the full error, because a timeout or
> IO failure means the run is inconclusive, not passing.
>
> 2. The deadline path did `first_refusal.unwrap_or_else(panic)`, returning a
> pass as soon as ONE refusal had been seen — so the "1 initial + 4 confirmations"
> guarantee stated in aceafb9's message could be satisfied with zero
> confirmations. Hitting the deadline is now always a panic, with a distinct
> message for "refused but only N of the required confirmations completed".
>
> The two interacted: because any `Err` counted as both a refusal and a
> confirmation, the confirmation mechanism added almost no discriminating power
> until (1) was fixed.
>
> MUTATION EVIDENCE, not inference. Stopping NATS entirely does NOT exercise this
> code — the test dies earlier at the SYS-account CONNECT guard (`:1210`,
> `Connection refused`), which is why the old defect survived. To reach the reject
> leg, the stack was left UP and only the reconnect target was pointed at a dead
> port, so setup succeeded and `connect()` returned `Io`:
>
>   attempt #1: fresh connect failed with a non-authorization error (kind=IO error,
>   full error: IO error: Connection refused (os error 61)) ...
>
> That configuration PASSED under the old code and now fails. The mutation was
> reverted and the live run re-confirmed green.

## Reading

The live S9 security test introduced in aceafb9 (the "revoke -> kick -> reject
under the < 5 s bar" acceptance test) was itself unsound in a way that would
have hidden the exact failure it existed to catch: a non-authorization
connect error — including a plain timeout against a dead or unreachable
target — was accepted as proof the revoked device had been refused, and one
refusal alone (not the claimed four confirmations) was enough to pass. The
commit is explicit that ordinary test runs never exercised this path, because
stopping NATS entirely fails earlier at a different guard; the defect only
surfaces when the stack stays up and only the specific reconnect target is
unreachable — a narrow, easy-to-miss configuration. This is a textbook
false-green in a security-critical acceptance test: the test was reporting
that revocation-based access denial worked when it had never actually
observed an `AuthorizationViolation`.
