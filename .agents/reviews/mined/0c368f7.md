## What the commit says

> A 9-byte payload could abort the process. The major-4 (array) and major-5
> (map) branches of `decode_one` passed an attacker-controlled count straight
> to `Vec::with_capacity` without ever checking it against the input. The
> byte-string and text-string branches immediately above already bound their
> length the same way this fix does — one file, two branches, only one
> guarding.
>
> Both reachable decode paths are pre-authentication:
>
>     payload = 9 bytes: [9b, ff, ff, ff, ff, ff, ff, ff, ff]
>     [1] signaling/mod.rs:101 -> Envelope::from_canonical_bytes
>         panicked at raw_vec/mod.rs:28:5: capacity overflow
>     [2] auth_token.rs:102 -> DeviceCertificate::from_canonical_bytes
>         panicked at raw_vec/mod.rs:28:5: capacity overflow
>
> Path [2] is inside the NATS auth callout that runs to *decide*
> authentication, so a peer that cannot authenticate can still reach it.

## Reading

This is the first fix produced by the 2026-09-02 bug-hunt audit (recorded in
288b608): a 9-byte pre-authentication payload could abort the entire process
via an unchecked `Vec::with_capacity` in the CBOR array/map decode branches,
while the two sibling branches (byte-string, text-string) in the very same
function already carried the guard that would have prevented it. This is the
canonical `missing-guard` shape the schema names — an invariant enforced in
one place and not its sibling, inside the same file. Because the vulnerable
code was reachable through the NATS auth callout itself, an attacker who
could never authenticate could still crash the host process before
authentication was decided.
