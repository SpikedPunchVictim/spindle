## What the commit says

> DESIGN.md §A7b:551 states the rule for signed artifacts: "version byte `v`,
> ... Unknown `v` => reject." The schema-of-record note below it narrows the
> artifacts carrying an explicit `v` to exactly three — Envelope, Capability,
> Admin command. Only Envelope enforced it (envelope.rs:276, reached from
> wire.rs:152,216,361). The other two carried `v` inside the signed preimage
> and never read it, identically in Rust and TypeScript — so there was no
> parity gap to lean on, just a documented requirement neither side met.
>
> An unenforced version floor cannot be added retroactively in the sense that
> matters: an old-version capability stays acceptable forever, because no code
> exists that could reject it. The whole value is in shipping it before the
> version you want to reject exists.

## Reading

A design-mandated invariant — "Unknown v => reject" for every signed
artifact carrying an explicit version byte — was implemented for one of the
three named artifacts (Envelope) and silently absent for the other two
(Capability, AdminCommand), identically in both language implementations.
This is a clean `missing-guard`: the same rule, enforced in one place and
not its two siblings. The commit adds a pointed note about why this kind of
gap is unusually costly to leave unfixed — a version floor has no
retroactive value, since by the time you want to reject a version it may
already be in circulation and accepted forever. The finding traces to the
2026-09-02 bug hunt (td-70c90b), which 2f68c268 records as re-verified and
strengthened from a mere code-absence claim into a violation of an explicit
documented requirement.
