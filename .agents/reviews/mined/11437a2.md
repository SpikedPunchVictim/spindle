## What the commit says

> td-ea075e (P2, security). The entitlements table was keyed on the raw literal
> subpath while grant EVALUATION folds, through
> VirtualPath::descends_from_or_eq -> confine::fold_key. So
> add_entitlement(g, s, "Photos") followed by remove_entitlement(g, s,
> "photos") deleted zero rows and returned Ok(()): a revocation that reports
> success without revoking, leaving a permission that still matches because
> the comparator that evaluates it folds. The ON CONFLICT clause had the
> mirror bug -- adding both spellings made two rows, and the member got the
> union.
>
> SCHEMA_V8 rebuilds the table with a fold_subpath column and moves UNIQUE,
> ON CONFLICT and DELETE onto it, keeping the literal subpath for display.
> This is SCHEMA_V7's fix one table over, and the fourth layer found keying
> on a path without folding.
>
> Proven by neuter: bypassing fold_key in both statements fails all three
> security tests on their real assertions -- the grant survives its revoke,
> and the upsert leaves two rows instead of one.

## Reading

This is a serious, already-shipped security defect: an admin who revoked an entitlement using a differently-cased spelling than it was granted with would see the call return success while the grant it meant to remove kept matching every future permission check, because evaluation folds case/Unicode but the storage and delete keys did not. The commit frames this as "the fourth layer found keying on a path without folding" — the same class of bug already fixed once for the upload identity table (SCHEMA_V7) and repeated elsewhere in this range (0bf6cb2's identity cache and upload-resume fix is the fifth). That pattern across four-plus independent layers strongly suggests a deliberate sweep for this exact defect class rather than one-off discovery, though the commit message itself does not use review language for finding this specific instance — only for verifying the fix afterward via an adversarially fault-injecting sub-agent.
