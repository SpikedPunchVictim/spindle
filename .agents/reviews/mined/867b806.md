## What the commit says

> 2. The pinning negative tests were not testing pinning
>
> Found by mutation: patching PinnedClientCertVerifier to accept every
> certificate left all 16 tests green. Client-certificate fingerprint
> pinning — a §A8 security property — could have been deleted from the
> codebase without a single red test.
>
> The tests asserted only is_err(). With pinning intact the server rejects in
> 0.01 s with TransportError(crypto(28), "client certificate fingerprint
> mismatch: ..."); with pinning removed, the handshake succeeds, accept_bi()
> waits on a stream the client never writes, and accept() fails after 30 s
> with Connection(TimedOut). Both are Err, so the assertion could not tell a
> correct rejection from thirty seconds of nothing.
>
> This was pre-existing: wrong_client_cert_is_rejected_by_the_server shipped
> in Stage 6 slice 5 and has been non-discriminating ever since, across a
> CI-green release. The production code was always correct; the guarantee
> that it would stay correct was not.

## Reading

A security-critical negative test for client-certificate pinning had shipped in Stage 6 slice 5 asserting only `is_err()`, which a 30-second connection timeout satisfies just as well as a correct 0.01-second rejection — so the test could not actually distinguish "pinning works" from "pinning was deleted." This shipped across a CI-green release and stayed unnoticed until mutation testing (deliberately patching the verifier to accept everything) proved all 16 tests stayed green anyway. The commit is explicit that the production code itself was never wrong; only the guarantee that a regression would be caught was missing. This is the textbook `false-green` case and the repo evidently treats it as a named pattern, since later commits in this range (03fc885, bc4f2bb) explicitly compare their own findings back to this one.
