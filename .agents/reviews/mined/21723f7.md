## What the commit says

> 0306dea fixed the S18 minting TOCTOU with a real database transaction but
> shipped a known gap: commenting out the `unchecked_transaction` left the
> entire suite green, so nothing in the gate could tell the fix from its
> absence. This closes that gap. Removing the transaction now fails
> `member_and_cap_epoch_never_returns_a_torn_member_epoch_pair_under_a_concurrent_revoke`,
> neuter-verified independently, 20/20 runs with no flake.
>
> The assertion is the self-consistency property, not the mechanism... Note this
> matters more than it looks. Because `member_and_cap_epoch` reads the epoch
> FIRST -- deliberate fail-safe ordering -- the neutered version tears into
> `(Revoked, epoch_before)`, not the `(Active, bumped)` pair one intuitively
> expects. An assertion written against that expectation would have passed
> against the bug.

## Reading

The prior commit (0306dea) had shipped a real fix for a serious TOCTOU but disclosed, in its own message, that the fix had zero regression coverage — the whole test suite passed identically whether the fix's core mechanism (a database transaction) was present or commented out. This commit closes that specific, self-reported gap by building a deterministic interleaving test using a SQLite `authorizer` callback fired at statement-prepare time, timed to land exactly in the gap the transaction is meant to close. It's also notable that the commit records a near-miss in its own test design: the first assertion shape considered ("never an Active member paired with the bumped epoch") would have passed against the very bug it targeted, because the deliberate epoch-first read order tears into a different, non-intuitive pair than the naive expectation. This is filed because it documents, in the implementer's own words, a coverage claim from a named prior commit that was real (disclosed, not hidden) but left a shipped fix unverifiable by the gate.
