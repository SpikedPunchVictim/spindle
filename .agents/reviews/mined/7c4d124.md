## What the commit says

> Found by adversarial review of 404315f + fe9ccd0, which rejected them.
>
> `uploaded_files.subpath` was plain TEXT with no COLLATE, so its primary key and
> both of `remove_uploads_under`'s match arms compared raw bytes. The rest of the
> VFS does not treat names that way. DESIGN.md:370-371: "creating a name that
> collides case-insensitively or under Unicode normalization with an existing
> dirent **is** an overwrite." `confine::fold_key` implements that rule and is
> already shared by `existing_entry_colliding`, `VirtualPath::descends_from_or_eq`
> and `glob`. The ledger re-decided the same question and answered it
> differently.
>
> On case-insensitive filesystems — macOS and Windows, the desktop host's primary
> targets — that produced two failures, both unhealable ...
>
> On Linux the counters stayed correct, because there really are two files.
> That is not a mitigation — it is a second bug, filed as td-48fb1d:
> `write_is_authorized` detects the fold collision and discards the colliding
> entry's actual name (`Some(_) => can_delete`), then `finalize_upload` renames to
> the *requested* spelling, so an overwrite that DESIGN.md authorizes as replacing
> one dirent instead leaves two. That is fixed next.

## Reading

An adversarial review of the two commits that added and wired up the upload
ledger (404315f, fe9ccd0) — explicitly said to have "rejected them" — found
that the new ledger table keyed its primary key and lookup queries on the
literal `subpath` string rather than on `confine::fold_key`, the folding
function every other name-identity comparison in the VFS already shares.
This is the exact pattern captured in this repo's own standing lesson that
"any layer keying on a path must use fold_key or it silently re-decides
DESIGN.md's dirent rule" — here the ledger re-decided it and got a different
answer, producing unhealable quota-counter corruption on case-insensitive
filesystems (macOS and Windows, the desktop host's primary targets). The
same review pass surfaced a second, related bug — `write_is_authorized`
discarding the colliding entry's real on-disk name so a rename-based
overwrite leaves two dirents instead of one — which the commit identifies
and files (td-48fb1d) but explicitly defers rather than fixing here.
