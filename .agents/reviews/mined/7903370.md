## What the commit says

> `decide_host_connect` verified the host op-key cert's chain-to-root,
> signature and `exp`, but nothing anywhere compared the cert's own
> `nats_fp` field against the nkey the connection actually authenticated
> with. `verify_host_op_key_cert` takes no `nats_fp` argument, and no
> caller made up the difference.
>
> That field is the whole session binding (DESIGN.md:286, :349). Without
> it, `verify_nkey_sig` only proves possession of whichever nkey is
> presenting -- not that it is the one the cert was issued for.
>
> The material to exploit it is not scarce. Every member `Capability`
> embeds `host_root_pk` + `op_cert` (DESIGN.md:306), and the embedded
> cert is issued with a dummy `nats_fp` and `exp: u64::MAX` because
> `verify_capability` never inspects it. So any member of a host could
> connect to NATS *as that host*, gaining `sub host.<h>.>`,
> `pub host.<h>.sess.*.*.h2c` and `pub registry.revoke.<h>`.
>
> Proven live before the fix, against `deploy/docker-compose.yml`: a
> freshly generated, unrelated nkey was admitted as the host using only
> `capability_op_cert()`.

## Reading

This is a severe, already-shipped authorization defect: DESIGN.md had specified a session-binding field (`nats_fp` inside the host op-key cert) since it was documented, but no verifier in the connect path ever compared it against the connecting nkey, making the binding a no-op. Any member holding a legitimate capability for a host — which is ordinary, intended possession, not a stolen secret — could impersonate that host on the NATS bus and gain its full host-scoped permissions. The commit proves this was exploitable, not theoretical, by demonstrating live admission of a freshly generated nkey against a running docker-compose stack using only material a normal member capability provides. This falls under "the implementer's own later audit" clause: nothing in the commit attributes the discovery to an external reviewer, but the defect had unambiguously shipped (it existed in the codebase this commit is fixing) and was found by re-examining the CONNECT authorization boundary against what DESIGN.md required.
