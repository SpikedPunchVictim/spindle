## What the commit says

> Adversarial review of 970b50f found that checked_verifying_key implemented only
> HALF of RFC 8032 5.1.3. It enforced y < p but not the second rule: when the
> decompressed x is 0, the sign bit must be 0 -- there is no negative-zero encoding.
>
> ...Measured on both sides:
>
>     bytes                                  Rust    noble
>     01 00..00 80  identity (0,1),  sign=1  ACCEPT  REJECT
>     ec ff..ff ff  order-2  (0,-1), sign=1  ACCEPT  REJECT
>     ec ff..ff 7f  same point,      sign=0  ACCEPT  ACCEPT
>
> So 970b50f's "both ends reject the same set" was false for those two strings.
> This is worse than the bug it replaced: y < 19 needed a signing key whose public
> y fell in a 12-value set (~2^-250, luck), whereas these two are constants an
> attacker writes straight into a sign_pk field.

## Reading

This is a textbook example of a security fix that was itself incomplete in a way that made the security claim actively false rather than merely unproven: the previous commit (970b50f) asserted parity between the two languages' key-canonicality checks, and review demonstrated two concrete byte strings where that assertion did not hold — and, worse, showed the residual gap was *more* exploitable than the original bug because it required no luck, just two known constants. The fix here replaces enumeration-by-rule (which missed a rule) with a round-trip re-encoding check that subsumes both RFC 8032 conditions by construction, and the commit explicitly credits the enumeration approach as "how the first attempt missed one." The secondary finding (F2) is a defense-in-depth gap in the TypeScript error-redaction wrappers that review found unreachable today but structurally fragile, given that Rust's equivalent type cannot express the same gap at all.
