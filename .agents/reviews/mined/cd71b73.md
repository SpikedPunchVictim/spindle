## What the commit says

> `reconcile_uploads_against_disk` was using the prefix removal, which is a
> category error: the sweep enumerates the ledger one row at a time and must
> heal exactly the row in front of it, since every descendant gets its own
> visit and its own decision. It is also a live bug once a directory can
> occupy a healed row's name -- ledger row `photos` healed while a separate,
> legitimate row `photos/a.jpg` exists for a real file uploaded into that
> directory would refund its uploader for a file still sitting on disk. Both
> sweep branches now go through remove_upload_row.
>
> Proven by neuter: reverting remove_upload_row to a prefix match fails both
> the store-level exactness test and the sweep-level subtree regression test;
> restoring the unresolved branch fails the rewritten directory test; deleting
> the is_dir check fails it with rows_resized=1 and member_upload_bytes=96.

## Reading

The reconciliation sweep shipped in 10cd65f reused `remove_uploads_under` — a prefix-matching helper correct for the VFS delete RPC, where deleting a directory must clear every ledger row beneath it — inside a per-row sweep loop that needed exact-row semantics instead. The mismatch was latent (it required a directory to occupy a name previously held by an uploaded file, plus a distinct sibling upload under that new directory) but real: a legitimate uploaded file's ledger row could be wrongly deleted and its uploader refunded a file that was still present on disk, purely because a sibling row's healing swept past it. The fix (`Store::remove_upload_row`, an exact `(share_id, fold_key(subpath))` delete) was verified by neutering back to the prefix match and confirming two tests fail. This is the same "reused the wrong-granularity primitive" mistake as several other fold/path bugs in this repo, just at the sweep layer rather than the identity layer.
