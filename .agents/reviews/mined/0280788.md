## What the commit says

> A ~5-8 KB pre-auth payload could abort the host process outright. Neither
> `decode_one` (Rust) nor `decodeOne` (TS) bounded its recursion depth:
> `grep -in "depth|recurs|MAX_NEST|nest"` across crates/spindle-proto/src/
> returned zero matches. A payload of N repeated 0x81 bytes (array, count 1)
> plus a terminal byte nests N deep in N+1 bytes.
>
> Measured against the real entry point `Envelope::from_canonical_bytes`, in
> a child process with the exit status checked -- a stack overflow is an
> abort, not a panic, so catch_unwind cannot see it:
>
>     release, 2 MiB stack (tokio's default worker stack):
>         depth  4000 -> exit 0, survived
>         depth  8000 -> exit 134, "fatal runtime error: stack overflow"
>     release, 8 MiB stack (main thread):
>         depth  8000 -> exit 0
>         depth 20000 -> exit 134
>     debug, 2 MiB stack (larger frames):
>         depth  1000 -> exit 134
>
> This is strictly worse than td-13c7dc, which produced a *catchable* panic.
> ...
> The count bound added in 0c368f7 does not help here: count=1 satisfies it at
> every level. Found by the independent adversarial review of that commit, then
> reproduced independently before being filed.

## Reading

An independent adversarial review of the just-landed CBOR count-bound fix
(0c368f7) found that the fix addressed only one dimension of the same
underlying vulnerability class: it bounded the declared element *count* per
level but did nothing about recursion *depth*, so a payload with count=1 at
every level of nesting still produced an uncatchable stack-overflow abort
rather than the catchable panic td-13c7dc had reduced the earlier bug to.
This is a `missing-guard` in the strict schema sense — the sibling protection
(a depth bound) simply did not exist next to the count bound the previous
commit added — discovered by a review process explicitly named as
independent and adversarial, then reproduced by the implementer before
filing and fixing.
